# Skill: generate-tri

## When to use this skill

Apply this skill when:
- The user confirms "yes, generate the TRI" after the interview phase
- The user asks to "generate the TRI document"
- Phase 1 (interview) is complete and all 12 questions have been answered

## Protocol — follow these steps exactly

This skill governs **Phase 2** of the Sage workflow.

---

### Step 1 — Read the template

The TRI template is available in your context as the `tri-template` skill.
Use it directly — do not attempt to read it from the filesystem.

---

### Step 2 — Fill every section

Map the interview answers to TRI sections using the table below.
Every section MUST be filled. If data is missing, write `[TO BE CONFIRMED]`.

| TRI Section | Source from interview |
|---|---|
| Service name (title) | Q1 |
| Project Management Owner | Q2 |
| Development Owner | Q2 |
| Approvers table | Q3 |
| Reviewers table | Q3 |
| Service Description | Q1 + Q5 |
| New Concepts and Terms | Q6 (component names) |
| Assumptions | Q4 |
| Success Metrics and Exit Criteria | Q5 |
| Architecture Diagram | Write: `[Architecture diagram to be added by the service team]` |
| Technical Design | Q6 |
| Trust Zones table | Q7 |
| Interfaces / Endpoints table | Q8 |
| Data Flows table | Q9 |
| Datastores table | Q10 |
| Service Dependencies table | Q11 |
| Components / Processes | Q6 |
| Vendors | Q11 (non-IBM third parties only) |
| Corporate Data, Privacy, and Tech Ethics | Derive from Q9 (PII/SPI presence) |
| Considerations for AI Applications | Q6 (AI/LLM usage) — fill only if AI is used |
| Reliability, Resiliency and Scalability | Q12 |
| Service Operations | Q12 |
| Security Impacts | Q12 |
| References | Write: `[To be added by the service team]` |

---

### Step 3 — Output format

Output the complete TRI as a fenced Markdown code block:

````markdown
# <ServiceName> — Technical Requirements Interlock (TRI)

[full TRI content here]
````

Then print below the block:

```
✅ Phase 2 complete — TRI generated for <ServiceName>.
Ready to save and open a PR. Shall I proceed?
```

---

### Step 4 — Save the file (Phase 3)

When the user confirms, use the MCP filesystem tool to write the TRI to:
```
/data/tri-output/TRI-<ServiceName>-<YYYY-MM>.md
```
(use the current year and month)

Then print:
```
✅ Phase 3 complete — TRI saved to /data/tri-output/TRI-<ServiceName>-<YYYY-MM>.md
Shall I open a Pull Request on GitHub to publish it?
```

---

### Step 5 — Open a Pull Request (Phase 4)

Execute these 3 tool calls **in order** — do not skip any:

**Tool call 1 — create_branch**
- owner: `SDANGELO`
- repo: `architecture`
- branch: `tri/<service-name>-<YYYY-MM>` (lowercase, spaces → hyphens)
- from_branch: `main`

**Tool call 2 — create_or_update_file**
- owner: `SDANGELO`
- repo: `architecture`
- branch: `tri/<service-name>-<YYYY-MM>` ← the branch just created, NEVER `main`
- path: `services/<ServiceName>/TRI-<ServiceName>-<YYYY-MM>.md`
- content: the full TRI generated in Phase 2
- message: `Add TRI for <ServiceName>`

**Tool call 3 — create_pull_request**
- owner: `SDANGELO`
- repo: `architecture`
- title: `TRI: <ServiceName> — <YYYY-MM>`
- body: `Automated TRI generated by Angelo – IBM Architecture Agent.\n\nService: <ServiceName>\nDate: <YYYY-MM-DD>`
- head: `tri/<service-name>-<YYYY-MM>`
- base: `main`

Then print:
```
✅ Phase 4 complete — PR opened at https://github.ibm.com/SDANGELO/architecture/pulls
```

- [ ] Service name in the title matches the name from Q1
